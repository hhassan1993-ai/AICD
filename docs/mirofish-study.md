# MiroFish — Architecture Study

Source: <https://github.com/666ghj/MiroFish> · HEAD read: `39d8491` (2026-09-03) · License: **AGPL-3.0**
Method: static read of the full source tree (128 files, ~48.7k LOC across `backend/**.py` and `frontend/src/**`). **Not executed** — no API keys, no Zep account. Every claim below is traceable to a file; runtime behaviour (LLM output quality, token cost, simulation fidelity) is *not* verified.

---

## 1. What it is

An LLM multi-agent **social simulation** engine. Input: unstructured seed documents (PDF/MD/TXT) plus a natural-language prediction requirement. Output: a populated temporal knowledge graph, a multi-round agent simulation on mock Twitter/Reddit platforms, and an LLM-authored report generated by a ReACT agent that queries the post-simulation graph.

The simulation kernel is **not** original: it is [OASIS](https://github.com/camel-ai/oasis) (`camel-oasis==0.2.5`, `camel-ai==0.2.78`) from CAMEL-AI. MiroFish's contribution is the **pipeline around** OASIS — automatic ontology induction, graph construction, persona synthesis, parameter generation, memory write-back, and report generation.

Backing: Shanda Group (盛大). Positioned as a decision-rehearsal sandbox (policy/PR stress testing) and a creative sandbox (the flagship demo deduces the lost ending of *Dream of the Red Chamber* from the extant 80 chapters).

## 2. Stack

| Layer | Technology | Notes |
|---|---|---|
| Backend | Flask 3 + flask-cors, app-factory pattern | `backend/run.py` → `app.run(threaded=True)`. Three blueprints: `/api/graph`, `/api/simulation`, `/api/report` |
| Frontend | Vue 3 + Vite 7 + vue-router + vue-i18n + axios + **d3** | No state library; no TypeScript. d3 drives the graph panel |
| LLM | `openai` SDK against **any** OpenAI-compatible endpoint | Default target is Alibaba Bailian `qwen-plus`. Optional second "boost" model (`LLM_BOOST_*`) used for the Reddit leg |
| Memory / KG | **Zep Cloud** `zep-cloud==3.25.0` (hard dependency) | `Config.validate()` explicitly *rejects* `ZEP_API_URL` — self-hosted Zep is unsupported |
| Simulation | OASIS (`oasis.make(...)`, SQLite per platform) | Twitter and Reddit environments run concurrently in one asyncio process |
| Persistence | **Filesystem only** | `backend/uploads/{projects,simulations,reports}/…` as JSON / JSONL / CSV. No RDBMS. OASIS keeps its own per-run SQLite |
| Packaging | `uv` + hatchling; Docker image `ghcr.io/666ghj/mirofish` | Python pinned `>=3.11,<3.13` |
| i18n | 7 locales in `locales/*.json`, including an `llmInstruction` per locale | Locale is threaded into prompts *and* into background threads via `set_locale` |

## 3. Pipeline

Five stages, mirrored one-to-one by the frontend wizard (`Step1GraphBuild.vue` … `Step5Interaction.vue`).

### Stage 1 — Ontology induction (`services/ontology_generator.py`, 732 LOC)
Documents are parsed (`utils/file_parser.py`, PyMuPDF + charset detection), chunked, and a **representative subset** of chunks is sampled under a character budget (`_select_representative_chunks`, `_calculate_excerpt_budget`) rather than sending the whole corpus. One LLM call returns candidate entity and edge types; `_validate_and_process` then coerces names to Zep's required casing (`PascalCase` for entities, `SCREAMING_SNAKE_CASE` for edges), strips reserved attribute names, and caps the count at `MAX_ONTOLOGY_TYPES`. `generate_python_code()` emits the ontology as Python source for inspection/download.

### Stage 2 — Graph construction (`services/graph_builder.py`, 879 LOC)
Chunks are ingested into a Zep **standalone graph** through the Batch API. The hard parts are all failure-handling:

- `build_operation_id(graph_id, chunks)` — a **content hash** used as an idempotency key. `_find_batch_by_operation_id` recovers an in-flight or completed batch instead of re-ingesting after a crash/retry.
- `_wait_for_batch` / `_wait_for_episodes` — two-phase barrier: batch accepted ≠ episodes indexed. The code waits for *episode* completion before declaring the graph usable (`ZEP_INGESTION_WAIT_TIMEOUT_SECONDS`).
- `_reconcile_batch_item_count` — detects silent item loss.
- `validate_batch_chunks(..., batch_size=350)` — pre-flight size guard.

Runs async on a thread, progress surfaced through the `TaskManager` singleton.

### Stage 3 — Environment synthesis (`services/simulation_manager.py` → `oasis_profile_generator.py` + `simulation_config_generator.py`)
1. `ZepEntityReader.filter_defined_entities` pulls nodes of the ontology's types out of the graph.
2. **Persona synthesis** (1,248 LOC): for each entity, a secondary Zep semantic search enriches the node's own summary (`_search_zep_for_entity`), then an LLM writes a full persona. Individuals and collective/abstract entities take **different prompts** (`_build_individual_persona_prompt` vs `_build_group_persona_prompt`) — a collective actor is not modelled as a person. Generated in parallel (default 3-wide) with **incremental flush to disk**, so a mid-run failure does not lose completed personas. Output formats are dictated by OASIS: **CSV for Twitter, JSON for Reddit**.
3. **Parameter synthesis** (993 LOC): deliberately *stepwise* — time config, then event config, then agent configs in batches, then platform config — explicitly to avoid one oversized generation failing. Ships a hard-coded Chinese-diurnal activity prior (`CHINA_TIMEZONE_CONFIG`: dead hours 00–05 at 0.05× activity, peak 19–22). Every LLM step has a rule-based fallback (`_get_default_time_config`, `_generate_agent_config_by_rule`).

### Stage 4 — Simulation (`services/simulation_runner.py` 2,033 LOC + `scripts/run_parallel_simulation.py` 1,699 LOC)
The Flask process **does not** run OASIS in-process. It `subprocess`-spawns `run_parallel_simulation.py` and supervises it. Inside that process:

- `oasis.make(agent_graph, platform=…, database_path=…, semaphore=30)` per platform; Twitter and Reddit run as concurrent asyncio tasks.
- Round 0 injects seed posts as `ManualAction(CREATE_POST)`; thereafter each round issues `LLMAction()` only to the agents the schedule marks active (`get_active_agents_for_round`), so wall-clock cost scales with the diurnal curve, not with population.
- Rounds are **simulated time**: `total_rounds = total_hours*60 // minutes_per_round`; each round carries a simulated hour/day.
- OASIS does not report what agents actually did, so actions are recovered by **tailing its SQLite DB by rowid** (`fetch_new_actions_from_db`, deliberately rowid rather than `created_at` to dodge timestamp-format drift) and re-hydrated with post/user/comment context before being appended to `{platform}/actions.jsonl`.
- **The environment is not torn down when the run ends.** It stays resident so agents remain interviewable.

Supervision side: `SimulationRunner` maintains `run_state.json`, monitors the child, and registers `atexit`/signal cleanup so orphaned simulation processes are killed when Flask dies.

### Stage 4b — Memory write-back (`services/zep_graph_memory_updater.py`, 791 LOC)
Every agent action is rendered to **natural-language prose** (`AgentActivity.to_episode_text`, with a per-action-type describer: `_describe_create_post`, `_describe_follow`, …) and pushed back into the same Zep graph as episodes, via a queue + worker thread with batching and a drain deadline. This is the design's keystone: the simulation's emergent behaviour becomes *queryable graph structure*, so the report agent reads seed facts and simulated facts through one interface, with Zep's bi-temporal edges distinguishing them.

### Stage 5 — Report + interaction (`services/report_agent.py` 2,619 LOC, `services/zep_tools.py` 1,734 LOC)
A hand-rolled ReACT loop — **not** LangChain, despite the module docstring claiming it, and **not** OpenAI native function calling. Tool calls are emitted as `<tool_call>{...}</tool_call>` in free text and recovered by `_parse_tool_calls` with two fallbacks for bare JSON; `_strip_fake_tool_results` removes tool *results* the model hallucinated into its own output.

Flow: `plan_outline()` → per-section `_generate_section_react()` (≤5 tool calls, ≤2–3 reflection rounds, temperature 0.5) → assembled Markdown. Four tools:

| Tool | Mechanism |
|---|---|
| `insight_forge` | LLM decomposes the question into ≤5 sub-queries → edge-scoped semantic search per sub-query + the original → dedupe facts → resolve every endpoint node of every returned edge → emit entity dossiers + `A --[REL]--> B` chains. Explicitly **untruncated**. |
| `panorama_search` | Breadth pass that *includes expired/invalidated edges* — reads Zep's temporal invalidation as history rather than noise |
| `quick_search` | Plain semantic search |
| `interview_agents` | Selects agents, generates questions, and **queries the live OASIS agents** through IPC |

Two log streams per report — `agent_log.jsonl` (structured: thought, tool call, tool result, section content) and a console log — both tailable by the UI via `from_line` polling and SSE-style stream endpoints. Post-generation, the user can chat with the report agent (≤2 tool calls/turn) or interview any simulated agent.

## 4. Cross-process control plane (`services/simulation_ipc.py`)

Because the OASIS environment must outlive the run and stay interactive, Flask needs to reach into the child process. The chosen mechanism is **file-based IPC**: Flask writes `commands/<uuid>.json`, the simulation loop polls that directory between/after rounds, executes (`interview`, `batch_interview`, `close_env`) and writes `responses/<uuid>.json`; Flask polls for the response with a timeout. Liveness is a status file (`check_env_alive`).

Assessment: crude but defensible — no broker, no port, survives Flask's reloader, trivially inspectable, and works identically on Windows (which the codebase treats as a first-class target, including monkey-patching `builtins.open` to force UTF-8 around OASIS's unencoded `open()` calls). Cost: polling latency, no backpressure, and correctness depends on the child reaching its poll point.

## 5. Engineering observations

**Strong:**
- Failure handling is where the effort went: content-hash idempotency on ingestion, two-phase ingest barriers, incremental persona flush, rule-based fallback behind every LLM step, JSON repair (`_fix_truncated_json`, `_try_fix_json`) on truncated model output, centralised retry (`utils/retry.py`, `utils/zep.py::call_zep_read_with_retry`).
- Decomposition of large generations into ordered small ones, to keep each LLM call inside a reliable output length.
- Process isolation of the simulation, with cleanup registered at interpreter exit.
- 18 backend test files, overwhelmingly targeting the Zep contract surface (paging, lifecycle, barriers, retry, error shapes) — i.e. the integration boundary most likely to break, not the easy pure functions.

**Weak:**
- **No CI runs the tests.** The only workflows are Docker image publish and a star-history cron. `pytest` appears nowhere in `.github/`.
- **The shipped Docker image runs the dev servers** (`CMD ["npm","run","dev"]` → Flask `app.run` + Vite dev). No WSGI server, no built frontend.
- `CORS(app, resources={r"/api/*": {"origins": "*"}})` with no authentication anywhere. There is no user/tenant model — every project, simulation and report is globally readable to anything that can reach the port. Fine for localhost, unsafe as deployed.
- Monolithic modules: `simulation.py` 2,878 LOC / 34 routes, `Step4Report.vue` 5,162 LOC. API and service layers are not cleanly separated (`api/graph.py` holds build orchestration, locks, and cascade-delete logic).
- Task state (`TaskManager`) is an **in-process singleton dict** — a Flask restart loses all in-flight task status, and it cannot survive being run multi-worker. Contrast with project/simulation state, which *is* persisted to disk.
- Text-parsed tool calls instead of native tool-calling: portable across arbitrary OpenAI-compatible endpoints (the stated design goal), but strictly more failure modes — hence `_strip_fake_tool_results` existing at all.
- Stale/incorrect docstring in `report_agent.py` ("使用 LangChain"); LangChain is not a dependency.
- Hard-coded cultural priors (Chinese diurnal rhythm) in a product marketed as universal.
- Comments and log strings are predominantly Chinese; the i18n layer covers user-facing strings only.

## 6. Ideas transferable to `rcp-coordinator`

Relevant because AICD is also "LLM agent orchestrating a long-running external process over a tool interface, streamed to a dashboard."

| Pattern | Where MiroFish does it | Applicability here |
|---|---|---|
| Content-hash idempotency key on expensive external writes | `GraphBuilderService.build_operation_id` | Directly useful if a phase ever re-runs against a live Revit MCP — a resumable `update_element_location` batch wants exactly this |
| Two-phase completion barrier (accepted ≠ applied) | `_wait_for_batch` + `_wait_for_episodes` | A real Revit write is asynchronous in the same way; "tool returned OK" is not "model updated" |
| Rule-based fallback behind every LLM step | `_get_default_time_config`, `_generate_agent_config_by_rule` | Already the AICD posture — its agent is deterministic by design. Worth keeping that way |
| Structured JSONL agent log + console log, tailed by `from_line` | `ReportLogger` / `ReportConsoleLogger` | AICD's WS log stream with backlog replay solves the same problem more cleanly; JSONL-on-disk adds crash-survivable replay |
| Decomposing one large generation into ordered small ones | `SimulationConfigGenerator` | Applies to any future LLM-authored output (e.g. a coordination report) |
| **Anti-pattern to avoid**: in-memory task registry beside on-disk domain state | `TaskManager` singleton | AICD is already in-memory-only and states so; the trap is *partial* persistence, not the absence of it |
| **Anti-pattern to avoid**: dev servers + `origins: "*"` + no auth in the shipped image | `Dockerfile`, `create_app` | AICD is localhost-scoped today; the cost of this shortcut arrives the moment it is not |

## 7. Bottom line

The interesting engineering is not the multi-agent simulation — that is OASIS, imported. It is the **glue**: turning arbitrary prose into a typed knowledge graph, that graph into OASIS-shaped personas and parameters, the resulting agent behaviour back into graph episodes, and that enriched graph into a cited report — with each step defended against LLM output that is truncated, malformed, or invented, and against an ingestion API that reports success before it means it.

The corresponding weakness is operational maturity: no test CI, dev servers in the production image, and no authentication or tenancy on an API that exposes every artefact it has ever produced.
